AGENTS.md — VYAPAAR project context

What this project is
VYAPAAR — a real full-stack application (not a demo/college project) that digitizes a wholesale garlic trading business: customers, suppliers, products, purchases, sales, payments, and udhari (credit) tracking. It will be used daily by a non-technical business owner. Correctness of money calculations matters more than speed of delivery.
Non-negotiable rules
Do not change the project architecture once a module is built. No "better approach" refactors mid-project.
Do not introduce enterprise patterns, extra abstraction layers, or design patterns not already in use. Keep classes small and simple.
Balances (customer/supplier) are NEVER stored as a mutable field. They are always computed fresh from sales/purchases/payments via `LedgerService`. If you ever find yourself about to add a `balance` column, stop — that violates the core design.
Package structure stays: `entity`, `repository`, `service`, `controller`, `config`, `exception`, `util`. Don't add new top-level packages without asking.
Complete and test one module fully (entity → repository → service → controller → manually verified via Postman or a quick curl) before starting the next. Do not build multiple modules in parallel.
After finishing each module: run the app, confirm it compiles and the relevant endpoint actually returns correct data, THEN report back to the user with what was built and how to verify it — do not silently continue to the next module in the same turn.
Never commit real secrets. DB password is `${DB\_PASSWORD}` env var, already fixed — do not reintroduce a hardcoded password.
Tech stack (fixed — do not deviate)
Backend: Java 21, Spring Boot, Spring Data JPA, MySQL, Maven, Hibernate
Frontend: React (Vite, TypeScript), Tailwind CSS v4 (theme via `@theme` in `src/styles/index.css`, not `tailwind.config.js`), react-i18next for Hindi/English
Testing: Postman for backend endpoints
Package base: `com.vyapaar`

Module 15, receipt delivery to the buyer: completed and live-verified on 2026-10-19. A receipt covers all of one customer's sales for one date, because sales are stored one row per product. `ReceiptService.getOrCreate` is idempotent on (customer, date): an existing receipt is returned untouched rather than regenerated, so a link already sent to a customer keeps working. `receipt_lines` holds an immutable snapshot of the products, quantities and rates at the moment the receipt was created, and `receipts.subtotal` is the total of that snapshot — this does NOT break the no-stored-balance rule, because a balance is a live fact that must be recomputed while a receipt is a document that must keep saying what it said when it was sent. `receipt_sends` is append-only audit. The PDF is rendered on demand by openhtmltopdf (the only new dependency, 1.0.10) from XHTML built with string concatenation in the style of `BillService`, and is never written to disk because Render's filesystem is ephemeral. Bundled Noto Sans and Noto Sans Devanagari fonts under `src/main/resources/fonts` are what make the rupee sign render at all; PDF built-in fonts have no rupee glyph. The buyer's link is `/receipt/{token}.pdf` — the `.pdf` ending is deliberate, because `SpaFallbackController` claims dot-free paths and would otherwise forward it to `index.html`. The token is 32 bytes from `SecureRandom` as URL-safe Base64, and it is a bearer token in a URL, so anyone it is forwarded to can read that one receipt. New env vars: `APP_PUBLIC_URL`, `BUSINESS_NAME`, `BUSINESS_PHONE` (all optional, with local defaults). WhatsApp delivery is a `wa.me` deep link that the owner sends from his own phone; no WhatsApp API, no credentials, no cost. Known limits
The receipt link is a bearer token in a URL. Anyone the buyer forwards it to can read that receipt, which shows that customer's items, quantities, rates and total for that one day. It never shows a balance and never shows another customer.
Per-sale bills (`BillService`, `/api/sales/{id}/bill`) and day-wise receipts (Module 15) now overlap. Bills are single-product plain text; receipts are multi-line PDFs. Decide later whether to retire the text bill.

Module 14, AI chat assistant (text-to-SQL): code complete on 2026-10-21. English, Hindi or Hinglish questions become ONE guarded read-only SELECT, which is run and then explained in plain language. Pipeline: `ChatController` (feature switch, then rate limit, then access code, then config check, then question length) -> `ChatService` (AI call 1 writes SQL) -> `ChatSqlGuard` (single statement, must start with SELECT or WITH, no comments, no stacked statements, no backslashes or backticks, forbidden-word list, and only the eight allow-listed tables and views; string literals are blanked first so `LIKE '%update%'` still passes) -> `ChatSqlRunner` (its own plain JDBC connection as the read-only MySQL user `vyapaar_chat`, `setReadOnly(true)`, 10s query timeout, 200 row cap) -> `ChatService` (AI call 2 explains the rows). A guard rejection triggers exactly one retry with the reason, then gives up. `ClaudeClient` uses Spring's own `RestClient`, so Module 14 adds NO new Maven dependency. The real security boundary is the database account, not the guard: `database/chat_readonly_user.sql` grants SELECT only, on six tables plus `v_customer_balance` and `v_supplier_balance`. Module 15's `receipts`, `receipt_lines` and `receipt_sends` are deliberately NOT granted and are rejected by the guard, because `receipts.public_token` is a bearer credential and a text-to-SQL surface must never be able to read a credential. Balance views live in `database/chat_views.sql` and repeat the `LedgerService` formula, so the assistant never invents a balance column; Hibernate does not create views, so that file is run by hand once per database. Prompt-injection handling: result rows are wrapped in a `<rows>` block with angle brackets stripped, phone columns replaced with `[hidden]`, at most 50 rows sent to the model, and the answering prompt states the rows are untrusted data. Frontend page `/chat` keeps the access code in `sessionStorage` only, shows a "Show SQL" button on every reply so the owner can see exactly what ran, and renders at most 50 rows. New env vars: `CHAT_API_KEY`, `CHAT_MODEL` (default `claude-haiku-5-5`), `CHAT_ACCESS_CODE`, `CHAT_DB_USERNAME`, `CHAT_DB_PASSWORD`. With `CHAT_ACCESS_CODE` empty the feature answers 503 and costs nothing, so it is safe to deploy switched off.
